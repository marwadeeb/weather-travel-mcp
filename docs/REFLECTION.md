# Reflection

I drew the boundary between my three tools by side effects. `get_weather_forecast` only reads: it calls Open-Meteo and returns typed daily data, and a test checks that calling it never touches the trips file. `save_trip_plan` is the only code that writes. It knows nothing about weather: it validates a date, rejects past dates and duplicates, and appends a record. `plan_trip` is the only tool that makes a decision. It fetches the forecast, scores each day on rain, temperature and wind, and saves the winner. Keeping the scoring out of the data tool was deliberate. Otherwise its description would have been "gets the forecast *and* recommends a day," which is exactly the "and" smell from class. Geocoding was the one judgement call. I kept it inside the data tool rather than making a fourth `geocode_city` tool, because the user never asks for coordinates and the assignment asked for exactly three tools. I documented it as an implementation detail. The orchestration tool calls the same internal helpers as the other two tools instead of going back through MCP. That keeps one source of truth for validation, and any failure from either step (an unknown city, an unavailable API, a day that is already saved) comes back as the same clear `ToolError`. If the forecast step fails, nothing is saved.

Three tools felt right for this scope. Each one maps to a distinct user intent ("what's the weather?", "save this exact trip", "pick a day for me"), so the agent rarely chose the wrong one. Read-only data, saved trips, is exposed as an MCP resource rather than a fourth tool. The main cost of the design is overlap between `plan_trip` and the other two tools. An LLM could reproduce `plan_trip` by calling the forecast tool and then the save tool itself. The orchestration tool is still worth having because it makes the ranking deterministic and testable instead of leaving it to the model. As next steps, I would add a `delete_trip` action so saved trips can be removed, let users set their own scoring weights (e.g. "I don't mind rain but hate wind"), support date ranges for multi-day trips, and serve the toolkit over streamable HTTP with authentication so several users or hosts could share it.
